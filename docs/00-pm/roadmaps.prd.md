# 공개 로드맵 PRD

## 1. 배경과 문제

프로필의 프로젝트 지도는 현재의 작업 표면을 보여 주지만, 공개적으로 추적되는 일이 어느 방향으로 가는지와 전달 흐름의 어느 단계에 있는지는 보여 주지 않는다. GitHub 프로필 안에서 공개 이슈만 근거로 삼아 프로젝트 방향과 개발 흐름을 읽을 수 있는 로드맵이 필요하다.

## 2. 대상 사용자

- 프로필 방문 중 현재 공개 작업의 방향을 빠르게 파악하려는 사람
- 공개 이슈를 작성·관리하며 프로필 반영을 기대하는 계정 소유자
- 공개 정보와 비공개 정보의 경계를 확인하려는 협업자

## 3. 핵심 가치와 성공 신호

- `Now · Next · Later`와 `Plan · Build · Verify · Ship` 두 관점을 한 번에 구분할 수 있다.
- 공개 이슈·라벨만 사용하고, 비공개 저장소·이슈·프로젝트 정보는 요청하거나 기록하지 않는다.
- 공개 이슈의 라벨이나 상태가 달라지면 정기 실행 또는 수동 실행으로 정적 자산이 갱신된다.

## 4. 범위(포함)

- 공개 GitHub Issues API 기반 로드맵 상태 수집
- TypeScript 기반 SVG·JSON 생성기와 단위 테스트
- 프로젝트 로드맵과 개발 로드맵 SVG 두 장
- 10개 언어 README의 단일 접기·펼치기 로드맵 패널
- 정기·수동·프로필 저장소 이슈 이벤트 기반 GitHub Actions 갱신
- 첫 공개 레이블 세트와 버전 태그·릴리스 발행

## 5. 비목표(제외)

- 비공개 저장소, 비공개 이슈, 비공개 Projects V2 정보 읽기 또는 표시
- 공개 이슈가 없을 때 임의의 미래 계획·진행률을 만들어 표시
- GitHub README에서 신뢰할 수 없는 JavaScript/hover 기반 상호작용
- 외부 유료 호스팅, 별도 서버, 장기 보관되는 API 응답

## 6. 사용자 시나리오

1. 방문자가 프로필의 로드맵 섹션을 읽어 두 관점과 데이터 경계를 이해한다.
2. 더 자세히 보고 싶으면 네이티브 접기 UI를 열어 두 SVG를 확인한다.
3. 계정 소유자가 공개 이슈에 `roadmap:*`와 `stage:*` 라벨을 붙인다.
4. 워크플로가 공개 API를 다시 읽고 변경된 로드맵 자산과 캐시 버전만 커밋한다.

## 7. 요구사항 목록

| ID | 요구사항 | 우선순위 | 수용 기준 |
| --- | --- | --- | --- |
| REQ-01 | 공개 이슈만으로 프로젝트·개발 로드맵 상태를 생성한다. | P0 | 두 SVG와 `data/roadmap-state.json`이 공개 소유 저장소의 이슈만 반영한다. |
| REQ-02 | 공개 이슈의 PR 항목과 포크·보관·비공개 저장소를 제외한다. | P0 | 생성 상태와 SVG에 해당 항목이 나타나지 않는다. |
| REQ-03 | `roadmap:now/next/later`와 `stage:plan/build/verify/ship` 라벨로 분류한다. | P0 | 라벨 조합에 따라 두 로드맵의 올바른 위치에 표시된다. |
| REQ-04 | 데이터가 없을 때 정직한 빈 상태를 렌더링한다. | P0 | 가짜 진행률·가상 일정·추론된 작업 카드가 없다. |
| REQ-05 | 모든 언어 README에서 하나의 접기 패널로 두 SVG와 텍스트 대체 정보를 제공한다. | P0 | 10개 README에 로드맵 제목, 두 로컬 SVG 링크, alt, `<details>`가 있다. |
| REQ-06 | 의미 있는 상태 변화가 있을 때만 SVG·JSON·캐시 버전을 갱신한다. | P0 | 같은 입력으로 두 번 실행해도 두 번째 실행에서 diff가 없다. |
| REQ-07 | GitHub API 일시 오류는 제한 재시도하고, 실패 시 기존 결과를 보존한다. | P1 | 타임아웃·408·429·rate-limit 403·502·503·504·네트워크 오류만 최대 3회 시도한다. |
| REQ-08 | 자동화는 명시적 allowlist 파일만 커밋하고, README 경쟁 갱신을 방지한다. | P1 | 워크플로가 공통 concurrency group과 명시적 `git add`를 사용한다. |
| REQ-09 | 최소 두 개의 버전 태그와 GitHub 릴리스를 제공한다. | P1 | 기준 릴리스와 로드맵 릴리스가 각각의 태그·설명과 함께 공개된다. |

## 8. 제약과 가정

- GitHub README는 네이티브 `<details>`와 정적 SVG만 안정적으로 지원한다.
- 공개 API를 사용하므로 별도 개인 액세스 토큰이나 Projects V2 권한이 필요하지 않다.
- 공개 이슈에 표준 라벨을 붙이는 행위는 계정 소유자가 통제한다. 자동화는 라벨·이슈를 만들거나 바꾸지 않는다.
- GitHub Actions 예약 실행은 UTC·기본 브랜치 기준이며, 수동 실행을 항상 함께 제공한다.

## 9. 미확정 항목

- 여러 공개 저장소에서 이슈 라벨을 통일할 운영 규칙: 첫 공개 이슈 생성 시 실제 사용 패턴에 맞춰 보완한다.
- Projects V2 기반 보드 표시: 별도 읽기 전용 권한이 필요한 후속 후보로 남긴다.

## 10. 변경 이력

| 버전 | 변경 내용 |
| --- | --- |
| v1 | 공개 이슈 라벨 기반의 정적 로드맵과 자동 갱신 요구사항 정의 |
| v2 | 공개 데이터 경계, 다국어 표시, 캐시 버전, 원격 실행과 프로필 렌더링 검증을 반영해 구현 완료 |
